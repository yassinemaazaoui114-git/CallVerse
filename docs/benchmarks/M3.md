# M3 benchmark: embeddings for Intake reasons and rule search (T23)

**Question:** M3 (`BAAI/bge-small-en-v1.5`) was chosen on 2026-10-14 without a benchmark. Is it the right model for
its two jobs, (1) Intake's reason matching and (2) the agents' rule search, and is plain dense search the right method?

**Method (HireSignal style):** simple baselines + candidates; everything tuned and chosen on **validation** sets with a
rule written **before** the results; then the two winners run **once** on **locked test** sets. 0 API calls, CPU only.
Code: `benchmarks/m3/`. Raw results: `benchmarks/m3/results/*.json`.

**Machine:** these numbers were measured on a **cloud machine** (4 CPUs, 15 GB RAM, Python 3.13.17, torch 2.15.0
**GPU build running on CPU**, 4 threads), not on Yassine's PC. Latencies and RAM will differ on the PC; the
**ranking** between models (same machine for all) is what matters. Peak RAM includes ~823 MB that Python + torch +
libraries take before any model is loaded (the GPU build of torch is large; the CPU build is smaller).

## 3. Intake (reason matching)

Matcher = a copy of `callverse/intake/reasons.py` (sentence split, each reason's score = mean of the top-k
similarities to its examples, best reason per sentence if ≥ threshold, "other" dropped if a specific reason is found,
main reason by the company's precedence order). A message where nothing passes the threshold counts as **needs the
LLM** = a miss (no API is called). Tuned on val per model: **top-k** ∈ {1, 3, 5} (one value for both companies, like
`config.yaml`) and a **threshold per company** in 0.40–0.90 (step 0.01); the best macro-F1 averaged over both companies
(ties: the middle threshold). Critical error = a money reason (ShopNova refund_request / return_item / damaged_item;
Atlas refund_request / compensation_request / cancellation) predicted as a non-money reason or the other way round.
Latency = one message alone, split + embed + score (after 10 warm-up calls), over all 368 val messages.

## 4. Rule search (each question in its own company's rules)

Methods: **dense** (each model; "title. text" for the rules like the system; with no prompt = today's way, and with the
model's documented query prompt), **BM25** (k1 1.5, b 0.75, written out, no library), **hybrid** (dense + BM25,
reciprocal rank fusion k = 60), **hybrid + reranker** (bge-reranker-base re-orders the hybrid top 10). Agents receive
2 rules, so **top-2** is the key measure. Latency = embed one question + rank (+ BM25 + fusion, + reranking 10 pairs).
"No-rule separable" = for how many of the 5 "no rule fits" questions the top score is **below** the lowest score of a
correct top-1 hit in the same company (i.e. a score threshold could have said "no rule"); report only.

## 5. Choosing rule (fixed before the results) and winners

- **Intake:** highest macro-F1 on val (ShopNova and Atlas averaged) among models with p95 ≤ 100 ms and peak RAM
  ≤ 1.5 GB; a tie (≤ 0.01) → the smaller model.
  → **bge-base-en-v1.5, top-k 1, thresholds ShopNova 0.70 / Atlas 0.51** (0.691; next eligible: bge-small 0.647,
  MiniLM 0.643, so no tie). Qwen3-0.6B was out on both limits (p95 147 ms, 2.35 GB) and was lower anyway (0.657).
- **Rule search:** highest top-2 on val (both companies together), then MRR, among methods with p95 ≤ 200 ms.
  → **dense bge-base + query prompt** (top-2 30/30, MRR 0.967). Tied exactly with Qwen3-0.6B + prompt; the tie went to
  the simpler, smaller one (written in the code: fewest parts, then fewest parameters).
- **Why the others lost:** today's setting (bge-small, k 3, 0.66 / 0.68) is 0.12 macro-F1 below and makes 58 critical
  errors on ShopNova val vs 25; MiniLM and tuned bge-small are close to each other but ~0.045 below bge-base; BM25 misses
  a third of the questions (customers do not use the rules' words) and fusing it in (hybrid) **pulls dense down** on these
  tiny rule sets; the reranker is as good as dense at top-1 but not better at top-2 and costs ~0.5 s per question here.
- **Today's setting did not win**, for either job. But for rule search the gap is small: today's dense bge-small misses
  1/30; the same bge-small **with its documented query prompt** reaches 30/30 (MRR 0.950).

## 6. What this means for the presentation

"Why bge-base and not bge-small?" — because on a fixed rule, with real customer messages from ABCD and a locked test,
the base model of the same family recognises the contact reason better (macro-F1 0.69 vs 0.57 for today's setting, about
half the money/non-money confusions) and still answers one message in ~55 ms on a CPU; and the same model, with its
documented query instruction, finds the right rule in the 2 rules the agent receives for 30/30 validation questions and
29/30 locked test questions. Bigger was not automatically better: Qwen3-0.6B (18× the parameters of bge-small) was
slower, heavier and not more accurate on Intake. Keyword search (BM25) and hybrid search, often recommended for RAG, are
worse here because 8–14 rules are too few for keywords to help and clients use their own words. Honest limits: the
ShopNova numbers are low for every model because ABCD labels are chat-level; the Atlas and rule-search sets are small
and AI-generated (one error = 2.5–3 points); the thresholds were tuned with "under the threshold = a miss", so they
send few messages to the LLM; times come from a cloud CPU, not the demo PC.

**Should we switch?** Yes, both point to one model, bge-base-en-v1.5, so the system still loads one M3. Switching would
change `config.yaml` (`intake.embedding_model`, `top_k: 1`, thresholds 0.70 / 0.51) and add the query prompt to the
rule-search query in `callverse/kb/search.py`; caches rebuild automatically. That is a separate step after Yassine's OK.

1134 MB); ABCD 37 MB (gz). Each embed_run takes 7–72 s on the cloud machine.

## 8. Decision on the demo PC (T24)

T23 picked **bge-base** by its rule on a cloud machine. T24 re-measured the system's own code on Yassine's PC
(torch 2.14.1 CPU build, 12 threads, validation sets only, `python -m benchmarks.m3.pc_check`):

| | bge-base (T23 choice) | bge-small, T23 val-tuned (kept) | Limit |
|---|---|---|---|
| Intake avg macro-F1 (val) | 0.6905 (= T23 0.691) | 0.6473 (= T23) | – |
| ShopNova critical errors (val) | 25 | 26 | – |
| Rule search top-1 / top-2 (val, 30 q) | 28 / 30 | 27 / 30 | – |
| **Intake p50 / p95 per message** | 76 / **134 ms** (rerun 70 / **124 ms**) | 40 / **60 ms** | p95 <= 100 ms |

**bge-base has the best quality, but its p95 of 124-134 ms on the demo PC is above the 100 ms limit, so it was not
chosen.** By the same T23 rule the next model within the limits is **bge-small**, now with T23's tuned settings
(`top_k` 5, thresholds ShopNova 0.69 / Atlas 0.54) and the BGE **query prompt** in rule search (query side only).
The PC numbers equal T23's val numbers, so the settings carry over. Revision pinned in `config.yaml`
(`intake.embedding_revision`). Raw PC results: `benchmarks/m3/results/pc_check.json` (bge-small) and
`pc_check_bge-base.json`. Leave-one-out on the 60 / 80 examples (report only): ShopNova 0.69 -> 40 exact, 5 wrong,
15 to the LLM of 60; Atlas 0.54 -> 62 exact, 17 wrong, 1 to the LLM of 80 (the benchmark thresholds were not changed).

**Rule fixed in advance (bge-small-ft must pass ALL):** avg macro-F1 >= 0.667: **pass** (0.678) · Atlas macro-F1 not lower than
today's: **fail** (0.853 < 0.884) · rule search top-2 stays 30/30: **fail** (22/30 without the prompt, 21/30 with it) ·

(PC less loaded), so the ranking of the speeds, not the absolute values, is what to read.
